---

BizHigher 블로그 업그레이드 작업. 이 저장소(BestLoanUSA/bizhigher)에서 기존 블로그 글 **1편**을 골라 깊이 있게 개선한다.

## 목표
잠재 고객(미주 한인 소상공인)이 구글에서 관련 질문을 검색하거나 ChatGPT·제미나이·구글 AI 요약에 물어볼 때 우리 글이 상위에 노출되고 인용되는 것. 그 글을 읽은 사장님이 "이 회사는 제대로 안다"고 신뢰하게 만드는 것. 노출 기술보다 **그 주제에서 인터넷에서 가장 정확하고 완결된 글**이 되는 것이 우선이다.

## 절차
1. `content/blog-upgrade-queue.md`에서 ⬜ 맨 위 slug를 고른다. 모두 ✅면 `updated`(없으면 `date`)가 60일 넘은 글 중 가장 오래된 것.
2. `content/blog/{slug}.md`와 `content/blog-calendar.md`의 '발행 스타일 가이드'를 읽는다. 같은 카테고리·연관 글의 제목과 slug를 파악한다.
3. **경쟁 분석**: 글의 핵심 검색어(한국어·영어)로 웹 검색해 상위 글 5~8개를 확인한다. 그들이 다루는 소제목·질문·표를 정리하고 우리 글에 빠진 것을 찾는다. 구글 "다른 사람들이 묻는 질문"류의 연관 질문도 수집한다.
4. **사실 검증**: 정책·화면·수치는 공식 문서(구글 비즈니스 프로필 도움말, Google Search Central, 광고 도움말, 옐프·메타 공식 안내, 관련 법규 원문)로 확인한다. 확인된 것만 쓴다. 출처 없는 통계, 확인 안 된 기능은 삭제하거나 "확인되지 않음"으로 처리한다. 바뀐 정책은 반영한다.
5. **글 개선**(아래 기준)을 적용해 같은 파일을 수정한다.
5-2. **이미지**: 글에 이미지가 없거나 1장뿐이면 `content/blog-calendar.md`의 '이미지 규칙'과 `design/infographic-templates/README.md`에 따라 인포그래픽을 1~2장 넣는다(이미 있는 글은 같은 유형 반복을 피해 부족한 만큼만). 렌더 후 PNG를 직접 열어 확인하고, 이미지 파일은 같은 커밋에 포함한다. 이미지를 못 만들어도 텍스트 개선은 그대로 발행한다.
6. 같은 카테고리 허브(`hub: true`)가 있으면 허브의 해당 요약·링크를 새 내용에 맞게 고치고 `updated`를 갱신한다.
7. `content/blog-upgrade-queue.md`의 행을 ✅ 오늘 날짜 + 한 줄 메모(무엇을 보강했는지)로 '업그레이드 완료' 표로 옮긴다.
8. 변경 파일을 하나의 커밋('blog: {제목} 업그레이드')으로 묶고, 푸시 전 `git fetch origin main && git merge origin/main` 후 main에 푸시한다.
9. 보고: 글 제목, URL(https://bizhigher.com/blog/{slug}/), 추가·삭제·수정한 핵심 내용, 확인 못 해 뺀 항목.

## 개선 기준
**검색 노출**
- 제목의 질문에 대한 **직접 답을 글 맨 앞 첫 문단**에 2~3문장으로 쓴다(AI와 스니펫이 그대로 인용할 수 있게).
- 검색자가 이어서 물을 질문을 소제목(`##`, `###`)으로 만들어 모두 답한다. 소제목은 사람이 실제로 검색할 문장형으로.
- 단계별 절차, 비교표, 점검표, 한인 가게 상황별 예시(식당·미용·안경·치과·학원·부동산 등)를 추가한다. 구체적인 문구 예시를 넣는다.
- 흔한 실수·주의사항·"이럴 땐 하지 마세요"를 솔직히 쓴다.
- FAQ(`## 자주 묻는 질문`)는 수집한 연관 질문 중 실제 수요가 큰 것으로 3~5개로 보강한다. 제목 문자열은 바꾸지 않는다.
- `description`(155자 내)은 클릭하고 싶게 다시 다듬고, `summary` 3문장 규칙(각 70자 이내, `|` 구분)을 지킨다. `keywords`에 한국어·영어 검색어를 보강한다.
- **내부 링크**: 관련 글 2~4개로 본문 맥락 안에서 자연스럽게 연결한다(`/blog/{slug}/`). 허브로 가는 링크도 둔다. 존재하지 않는 slug는 링크하지 않는다.
- 외부 링크는 구글·공식 문서 같은 1차 출처로 1~3개, 필요한 곳에만.
- 길이 제한은 없다. 주제가 요구하는 만큼 쓰되 반복·군더더기·키워드 채우기는 넣지 않는다. 길이가 늘수록 읽기 쉬워야 한다(표, 목록, 짧은 문단).

**AI 인용**
- 모호한 말 대신 **단독으로 인용돼도 뜻이 통하는 단정문**을 쓴다. "~는 ~입니다" 형식, 조건과 예외를 함께.
- 용어는 처음 나올 때 한 줄로 정의한다. 날짜·기준 시점을 명시한다("2026년 10월 기준").
- 표와 번호 목록을 적극 쓴다(구조화된 정보가 인용되기 쉽다).

**신뢰**
- 존댓말, 미국 한인 사장님 눈높이. 과장·단정적 보장("무조건", "1위 보장") 금지.
- 직접 해본 적 없는 경험담, 가상의 고객 후기, 지어낸 수치·사례를 쓰지 않는다. 예시는 "예를 들어"로 가상임을 분명히 한다.
- 변경 이력을 위해 실제 내용을 고쳤을 때만 `updated:`를 오늘 날짜로 넣는다.

## 지켜야 할 것 (어기면 작업 실패)
- `slug`, 파일명, `date`, `category`, `related`는 바꾸지 않는다. `title`은 의미를 유지하되 검색 의도에 맞게 다듬는 정도만(순위가 쌓인 URL 보호).
- **본문에 판매·홍보 문구, 회사 소개, 가격, "저희에게 문의하세요"를 넣지 않는다.** CTA는 빌드가 자동 부착한다(CLAUDE.md §9).
- 리뷰 대가 제공·리뷰 게이팅·가짜 리뷰·정책 우회 방법을 권하지 않는다. 의료·치과 글은 환자 여부 암시 금지(HIPAA).
- 키워드 반복 채우기, 숨은 텍스트, 의미 없는 문장 늘리기 금지(구글 스팸 정책 위반으로 순위 하락).
- 이미지: 지어낸 수치·가짜 화면·판매 문구가 들어간 이미지는 쓰지 않는다. 렌더 확인 없이 넣지 않는다.
- 한 번에 글 1편만. 다른 글은 내부 링크 확인 목적 외에는 수정하지 않는다.
- `data/services.json`과 `functions/`, `build.js`는 건드리지 않는다.
- 커밋 전 확인: front matter 형식 유지, summary 줄 1개·세 부분, `## 자주 묻는 질문` 존재, 깨진 내부 링크 없음.
- 확인 불가한 사실이 많아 글을 안전하게 개선할 수 없으면 파일을 바꾸지 말고 이유를 보고한다.

## 대기열 외 제안
업그레이드 중 우리 블로그에 없는 중요한 검색 주제(예: 한인 마케팅 회사 고르는 법, 업종별 가이드)를 발견하면 글을 쓰지 말고 `content/blog-calendar.md` 발행 대기열 **맨 아래에만** 제안 행을 추가한다(제목·카테고리·related, 한 줄 이유).
