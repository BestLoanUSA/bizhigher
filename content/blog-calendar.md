# BizHigher 블로그 발행 캘린더 (레포 내 운영본)

운영: 월·수·금 자동 발행 루틴이 이 파일을 읽고 **대기열 가장 위의 ⬜ 주제**로 글을 쓴 뒤, content/blog/에 md 파일을 추가하고 이 파일의 해당 행을 ✅로 갱신하여 한 커밋으로 푸시한다. 푸시되면 Cloudflare가 자동 배포한다.

## 발행 스타일 가이드 (루틴 필독)

- 파일 위치: content/blog/{slug}.md
- frontmatter: title, slug(영문), date(오늘), description(155자 내), **summary(핵심 요약 3문장)**, keywords, category, related(서비스 slug)
- **summary 규칙 (2026-10-06 도입)**: `summary: 문장1 | 문장2 | 문장3` 한 줄. ` | `로 정확히 세 문장, 각 70자 이내, 문장 안에 `|` 금지, 값이 `"`로 시작하지 않게. 문장1 = 제목 질문에 대한 직접 답, 문장2 = 핵심 기준·숫자·이유, 문장3 = 첫 실행 단계 또는 솔직한 주의사항. 맥락 없이 따로 인용돼도 뜻이 통하는 단정문으로, 본문에 있는 사실만 쓰고 판매 문구 금지. 빌드가 글 맨 위 "핵심 요약" 박스와 BlogPosting abstract로 자동 출력한다
- 본문: **최소 1,800자, 상한 없음 (2026-10-21 David 결정)**. 길이를 맞추려 하지 말고 주제가 요구하는 만큼 깊이 쓴다. 목표는 해당 주제를 구글에 검색했을 때 우리 글이 최상단에 오르는 것 — 검색자가 다른 글을 더 볼 필요가 없을 만큼 완결된 글이어야 한다. ## 섹션은 4개 이상(상한 없음) · 표 또는 체크리스트 1개 이상 · 마지막에 `## 자주 묻는 질문` 섹션(### 질문 3~5개 — FAQ 스키마로 자동 추출됨)
- **깊이 기준**: 주제를 고른 뒤 웹 검색으로 현재 상위 노출 글들이 다루는 항목을 확인하고, 그것을 모두 포함한 뒤 그 위에 (1) 단계별 절차, (2) 한인 가게 사례·예시 문구, (3) 흔한 실수와 주의사항, (4) 직접 해볼 수 있는 점검표를 더한다. 최신 사실은 공식 문서(구글·OpenAI 등)로 확인하고, 확인 안 되는 수치는 쓰지 않는다
- **주제 선정 기준**: 사장님이 실제로 검색할 질문 / 손해·정지·법적 위험이 걸린 문제 / 기존 글에 없는 구체적 절차·숫자·점검표 — 셋 중 둘 이상 충족. 기존 글과 겹치면 새 관점이 있을 때만 쓴다
- **AI 검색 주제는 지속적으로 확대한다** (David 결정 2026-10-21): 대기열에 AI 검색 카테고리 글이 항상 2개 이상 있도록 유지
- 톤: 존댓말, 미국 한인 사장님 눈높이, 과장 금지, 솔직한 주의사항 1개 이상, 모든 주장에 실행 단계·판단 기준
- 본문에 판매 문구 금지 (CTA는 빌드가 자동 부착: 무료 진단 + related 서비스)
- category 풀: 구글 노출 / 리뷰·평판 / 콘텐츠·SNS / 광고 / 웹사이트 / AI 검색
- 이미지: `![캡션](/blog-img/파일명.png)` — 이미지 파일은 content/blog/img/에

## 이미지 규칙 (2026-10-21 도입, 발행·업그레이드 루틴 공통, 필독)

- **글당 이미지 1~2장.** 인포그래픽 템플릿(`design/infographic-templates/`)에서 주제에 맞는 것을 골라 만든다. **선택표·사용 순서·숫자 규칙은 `design/infographic-templates/README.md`를 먼저 읽고 그대로 따른다.**
- 같은 유형이 최근 글 3편 안에 반복되지 않게 한다. 숫자 없는 구조형 템플릿을 우선하고, 출처 없는 숫자는 쓰지 않는다.
- 파일은 `content/blog/img/{slug}-{키워드}-{템플릿}.png`, 본문은 `![한 문장 설명](/blog-img/파일명.png)`. 이미지 속 내용은 본문에도 글로 있어야 한다.
- 렌더 후 PNG를 직접 열어 한글 깨짐·겹침을 확인한다. 못 고치면 이미지 없이 발행하고 보고에 사유를 적는다(이미지가 글 발행을 막지 않는다).
- **이미지 파일은 글과 같은 커밋에 포함한다**(`git add content/blog/img`).

## 허브 글 규칙 (2026-09-22 도입, 루틴 필독)

카테고리별로 글이 쌓이면 "허브" 글로 묶는다. 허브는 frontmatter에 `hub: true`가 붙은 평범한 블로그 글이다 — **스포크(일반) 글 쪽은 손댈 필요가 없다.** build.js가 같은 카테고리의 `hub: true` 글을 자동으로 찾아 스포크 글 상단에 "이 글은 OOO 가이드의 일부입니다" 링크 박스를 붙이고, 블로그 인덱스에서도 허브를 "🧭 핵심 가이드" 섹션에 자동으로 분리해 보여준다.

새 글을 하나 발행할 때마다 다음을 같은 커밋에서 함께 확인한다:

1. **이번 글 카테고리에 이미 허브(`hub: true`)가 있는가?**
   - 있으면 → 그 허브 .md 파일 본문에 이번 글 요약 1~2문장 + 링크를 알맞은 섹션에 추가하고, frontmatter `updated:`를 오늘 날짜로 갱신한다.
   - 없고, 이번 글까지 포함해 해당 카테고리 글이 **3개 이상**이 되면 → 새 허브 글을 만든다. 파일명은 `{category-slug}-hub.md`, frontmatter에 `hub: true` 추가, 본문은 기존 스포크 글들을 단계별/상황별로 안내하며 각각 요약+링크. 표 또는 체크리스트 1개, FAQ 섹션 등 일반 글과 동일한 스타일 가이드(1,800자 이상, `##` 4~7개)를 그대로 따른다 — 단순 링크 모음이 아니라 그 자체로 완결된 개요 글이어야 한다.
   - 카테고리 글이 아직 3개 미만이면 허브를 만들지 않는다.
2. 허브 글 자체는 대기열에서 순서를 차지하지 않는다 — 카테고리 조건 충족 시 그때그때 만드는 것이지, 대기열 항목이 아니다.
